# ADR-0001: An open, federated protocol, not an API or SaaS

**Status:** accepted (2026-08-04)

## Context
The problem (tasks generated by third parties arriving disorganised) could be attacked with a product: an app with a public API for companies to integrate with. It is the path of least effort and the one the whole market has tried (Todoist, TickTick, Google Tasks), always ending in silos where the issuer has to integrate with every platform and the user is locked into one.

## Decision
e-work is a protocol, in the sense of IMAP, SMTP and MQTT: an open specification, multiple independent client and server implementations, federation between servers, and the possibility of self-hosting or of public providers, with no privileged node.

## Alternatives considered
- **SaaS with an open API:** rejected. It reproduces the silo; the issuer integrates with a vendor, not with an ecosystem; the death of the company means the death of the data.
- **A format specification only (a ".task file")**: rejected. A format without a protocol for delivery, consent and status solves none of the reference scenarios.

## Consequences
- Success depends on network effects; the adoption strategy (bridges, an issuer gateway, the bill case) becomes part of the design, not a detail.
- Every technical decision has to be implementable by third parties from the text alone: no magical reference behaviour.
- Governance of the specification has to be resolved before publication (recorded in RFC 0000).
