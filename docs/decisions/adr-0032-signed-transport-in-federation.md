# ADR-0032: Delivery is signed by the host of the `from` domain, and the envelope proof is bound to that key

**Status:** proposed | 2026-10-21 | awaiting Michel Wilhelm

## Context

EW-RFC 0005 §2 requires two layers of authentication in federation: transport, by HTTP Message Signatures (RFC 9421) with the `hostKey` of the `from` domain, and object, by the author's proof inside the envelope. It also requires the receiver to validate both and `from` to be consistent with whoever signs the object.

Read in the code on 2026-10-21, the reference host did only half of the second layer. The inbox received the JSON body without headers and called `verify_author`, which checks the envelope proof against the key the proof itself declares, and nothing else; nothing tied that key to the `from` domain. Delivery, on the other side, went out with no signature at all. In practice, a key generated on the spot was enough to send, in the name of any domain:

- a consent request, which lands in the person's quarantine saying that "Acme" wants to send tasks;
- a revocation from a relationship address, which makes the issuer mark as revoked a relationship the person never ended: whoever knows the address ends other people's relationships;
- a grant and a project invitation, which only the textual `from` of a relationship separated from the rest;
- and the envelope the edge keeps as proof of what it refused was the word of a key anyone can generate.

The offer had one defence, the send capability, which is a bearer token: leaked, it delivered from anywhere.

Three facts shape the fix:

1. The RFC 9421 profile lives in EW-RFC 0004 §1.1, and it was written for opening a session, where the host issues a challenge and the signed nonce has to be the host's. Delivery has no challenge. The RFC also did not say what goes in `keyid` or where the receiver takes `@target-uri` from.
2. There are three reference hosts in production (`imake.codes`, `dainner.app`, `eworkprotocol.org`), updated by the same release but one after the other, and the protocol is open: there may be others. A receiver that starts requiring the signature before the senders sign refuses the whole federation during the update window, and a host that rolls back to the previous version is left out until it updates again.
3. The reference host has signed the envelope with its own key since the first commit, for everything it composes. The exception is the consent request, which the client composes and signs (`Consent/knock`), and which the Python library posted straight into the destination inbox, without going through the host.

## Decision

**Delivery is signed by the `hostKey` of the `from` domain, and that key is what binds the envelope proof to the address.** The normative text is in EW-RFC 0005 §2.1 and §2.2.

1. **Profile.** RFC 9421 with the EW-RFC 0004 §1.1 set. Without a challenge, the `nonce` is generated by the signer, new for every request and every retry, and the receiver keeps what it accepted until the signature can no longer be valid. `keyid` is the `from` domain. `@target-uri` is the `federationInbox` the destination announces, and the destination rebuilds it from what it announces itself, never from the request's `Host`.
2. **Where the key comes from.** From the discovery document served by the `from` domain itself (EW-RFC 0001 §3.3, path 2), authenticated by that domain's TLS. The reference host does not follow SRV, which is why the delegation proof of EW-RFC 0001 §3.2, not yet implemented, is not required on this path. The key is kept for a day, with at most one forced fetch per domain per minute when the signature does not verify. The fetch is treated as a network proxy (EW-RFC 0010 §3).
3. **Consistency between `from` and the object signer, in two forms.** Either the proof is by the `hostKey` of the `from` domain itself, which is the host speaking for its addresses and the only form that verifies after the hop; or the proof is by another key and the hop came signed by that `hostKey`, which is the domain vouching for its client's key, the way DKIM vouches for the local part of an address.
4. **Refusal.** `unauthorized`, before any lookup of the recipient, and retryable.
5. **Transition in two steps, as a stack of two pull requests.**
   - **Step 1.** Every host signs. The receiver verifies the signature when it is present, and refuses an invalid one. Without a signature, from another domain, it accepts with a log warning only the envelope whose proof is by the `hostKey` of the `from` domain (what every reference host has always sent) and the consent request (the only one an old host sends with a proof by another key); it refuses everything else, and refuses any unsigned envelope in the name of its own domain. The Python library knocks through the host.
   - **Step 2.** The signature becomes required for every delivery. The criterion for merging is operational: after the step 1 release, the production hosts' logs go a few days without a single "sem assinatura de transporte" line.

## Alternatives considered

- **One challenge per delivery, as in the session.** Rejected: it doubles the round trips of every delivery, makes the inbox keep state per sender before knowing who it is, and the challenge request would need authentication too. The nonce memory gives the same guarantee without the extra trip.
- **No nonce, only the five-minute window and idempotency by `id`.** Rejected: the nonce is part of the closed set of §1.1, and dropping it would mean a second RFC 9421 profile in the same protocol. Idempotency by `id` is a rule about effect, not about authentication: it says that a second identical envelope changes nothing, not that the request came from whoever it claims.
- **`keyid` carrying the key itself, or the document URL.** Rejected: the receiver resolves the key through the `from` domain anyway, and a `keyid` carrying the key invites checking against the key the request chose. The domain gives the receiver one more check, and makes the batch rule writable: one batch, one domain.
- **Requiring the identity document of the signer of every proof not made by the host.** Rejected: the per-relationship address is deliberately not linked to the root (ADR-0022), a device key cannot be found without exposing the root, and the host of the `from` domain already vouches for the key when it signs the hop. Requiring more would close the consent request path or publish what ADR-0022 hides. Whoever needs to link the key to a person can still check that person's document.
- **Requiring every envelope proof to be by the host key.** Rejected: it closes the door on the end-to-end author proof EW-RFC 0001 §5 wants, the one that survives relay and migration, and the consent request is legitimately signed by the client.
- **Requiring the signature right away, in one switch.** Rejected: the three hosts update in sequence within the same release, and any of them rolling back to the previous version is left unable to deliver. Since `unauthorized` is not a permanent error, the damage would be delay rather than loss, but a version rollback would become a federation outage.
- **Announcing in the discovery document that the host signs, and requiring it from whoever announces.** Rejected: it would register in the closed vocabulary of EW-RFC 0001 §8 a capability that only means something during the transition, and a registered value never leaves.
- **Remembering which domains have already sent signed deliveries and requiring it from them.** Rejected: it is state that only serves the transition, and a host rolling back to the previous version would have its deliveries refused with no message saying why.
- **A configuration option to require the transport signature.** Rejected: with a permissive default, the non-conforming behaviour becomes the default forever; with a strict default, every host would need an infrastructure change during the transition. The stack separates the two moments without a knob.

## Consequences

- The production hosts keep talking during the update, in both directions: the old inbox ignores the new headers, and the new inbox accepts what the old host sends.
- Step 1 already closes revocation, grant, invitation, offer and status in the name of another domain, and any envelope in the name of the receiver's own domain. Only step 2 closes the forged consent request in the name of another domain.
- The envelope kept as proof of what the edge refused now verifies against the key the issuer's domain publishes.
- Each receiver fetches the `hostKey` of each sending domain once a day, plus at most one forced fetch per minute, and keeps two new tables: `chaves_de_dominio` and `nonces_de_transporte`.
- Changing a host key no longer kills what is queued: the transport signature is made again at every attempt, already with the new key, and the envelope signed with the old one passes through the second form of consistency. The change shows in the receiver's log as a suspicious change (EW-RFC 0001 §3.2); surfacing it to the person is still to be done.
- The key fetch is SSRF surface, and the guard, like the gateway's, checks names and literal IPs. Filtering the resolved address was left for later, because it depends on each host's resolver not returning an internal address for an external domain, and that is exactly what split DNS does.
- The Python library knocks through the host (`Consent/knock`), and the return value of `knock` changed: it is the call's response, no longer the HTTP status of the remote inbox.
- The `bench/` scripts that post forged envelopes straight into the inbox now get `unauthorized` before the consent edge. What they measured still holds for an attacker with their own host and a published key, and that is the attacker they need to simulate from now on.
- Fetching attachments between hosts still uses its own scheme, older than this profile, and the profile for GET became open question 4 of EW-RFC 0005.
